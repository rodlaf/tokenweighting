\section{Experiments}\label{sec:experiments}

\subsection{Scope and Reproducibility}

The repository now implements the experiments described in this paper as runnable
Qwen-based training jobs rather than as a synthetic benchmark. We intentionally do not
report fabricated numbers here: the code, configs, and evaluation harness are included
in the repository, and the actual tables should be populated from completed runs.

\subsection{Models}

Our reference math model is \texttt{Qwen/Qwen2.5-Math-1.5B-Instruct}. Our reference code
model is \texttt{Qwen/Qwen2.5-Coder-1.5B-Instruct}. Both are trained with LoRA adapters
and optional 4-bit loading so that the experiments fit on modest hardware.

\subsection{Tasks and Rewards}

\paragraph{GSM8K.}
We use the \texttt{gsm8k/main} split as the primary benchmark. Each prompt is formatted
as a reasoning task with an explicit final-answer convention. The reward is binary: it
is $1$ iff the extracted final numeric answer matches the reference answer after
normalization, and $0$ otherwise.

\paragraph{MBPP.}
We also implement a code benchmark using MBPP. The model is prompted to return Python
code, and reward is binary pass/fail under the task's unit tests. Because arbitrary code
execution is involved, the repository uses a lightweight timeout-based subprocess
harness; users may substitute a stronger sandbox when running larger sweeps.

\subsection{Methods Compared}

The implemented training variants are:
\begin{itemize}
    \item \textbf{RLOO + uniform weighting}
    \item \textbf{RLOO + surprisal weighting}
    \item \textbf{RLOO + entropy-reduction weighting}
    \item \textbf{GRPO + uniform weighting}
    \item \textbf{GRPO + surprisal weighting}
    \item \textbf{GRPO + entropy-reduction weighting}
\end{itemize}
All methods share the same rollout count, prompt formatting, optimizer family, and
decoding hyperparameters within a task. This isolates the effect of token-level credit
redistribution from unrelated implementation changes.

\subsection{Training Procedure}

The main experiment entrypoint is \texttt{experiment/run\_experiment.py}. For each
minibatch of prompts, we sample $K$ completions from the current policy, compute binary
rewards after full generation, construct either RLOO or GRPO prompt-level advantages,
and then apply the weighted token-level objective from Section~\ref{sec:methods}. The
code recomputes token log-probabilities under teacher forcing for the sampled
completions and then applies one of three within-trajectory weighting rules: uniform,
surprisal, or entropy reduction.

The repository ships explicit YAML configs under \texttt{configs/experiments/}. For
example:
\begin{itemize}
    \item \texttt{qwen25-math-1.5b-gsm8k-rloo-uniform.yaml}
    \item \texttt{qwen25-math-1.5b-gsm8k-rloo-surprisal.yaml}
    \item \texttt{qwen25-math-1.5b-gsm8k-rloo-entropy.yaml}
    \item \texttt{qwen25-math-1.5b-gsm8k-grpo-uniform.yaml}
    \item \texttt{qwen25-math-1.5b-gsm8k-grpo-surprisal.yaml}
    \item \texttt{qwen25-math-1.5b-gsm8k-grpo-entropy.yaml}
\end{itemize}
Equivalent MBPP configs are provided for the code setting.

\subsection{Metrics}

The code records the metrics needed for the paper's main comparisons:
\begin{itemize}
    \item \textbf{Greedy accuracy}: deterministic correctness on held-out prompts.
    \item \textbf{Pass@$k$}: success rate over $k$ sampled completions.
    \item \textbf{Reward mean / variance}: rollout-level training diagnostics.
    \item \textbf{Completion length}: to monitor drift in response style.
    \item \textbf{Token-weight statistics}: average weight concentration under each
    intrinsic rule.
\end{itemize}
For GSM8K, correctness is exact-answer match. For MBPP, correctness is unit-test pass
rate.

\subsection{How to Populate Final Tables}

Because the current revision is meant to be honest about what has and has not been run,
the paper tables should be filled only after executing the provided configs. A minimal
first pass is to run the six GSM8K configurations above and report greedy accuracy plus
pass@4 on the chosen evaluation slice. The same procedure can then be extended to MBPP.

\subsection{Compute Considerations}

The implementation is intentionally compact: intrinsic token weights are computed from
quantities already produced by the policy during rollout or the subsequent
teacher-forced forward pass. No learned critic, reward model, or search tree is
required. This keeps the experiments aligned with the paper's central claim while
remaining practical to run on limited hardware.
